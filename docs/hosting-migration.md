# Переезд с GitHub Pages на российский хостинг

## Что случилось

17–18 августа 2026 до сайта переставала доезжать примерно **треть**
оплаченного рекламного трафика:

| День | Клики (оплачены) | Визиты в Метрике | Потеряно |
|---|---|---|---|
| 15.08 | 125 | 116 | 7 % |
| 16.08 | 114 | 112 | 2 % |
| 17.08 | 154 | 57 | **63 %** |
| 18.08 | 75 | 25 | **67 %** |

Проверка с телефона владельца:

* через **мобильный интернет** сайт открывается;
* через **проводного провайдера** — «Превышено время ожидания ответа».

Соединение устанавливается, но ответа нет — это фильтрация на стороне
оператора, а не поломка сайта. Домен `налог-сервис.рф` (punycode
`xn----7sbhcltqolxje.xn--p1ai`) A-записями смотрит на GitHub Pages:

```
185.199.108.153  185.199.109.153  185.199.110.153  185.199.111.153
```

Эти адреса у части российских операторов недоступны. Пока сайт лежит на
них, проблема воспроизводится у непредсказуемой доли аудитории.

## Решение

Отдавать сайт с российского адреса. Сборка не меняется: это статический
SPA на hash-роутере, сервер ему не нужен — нужен только тот, кто отдаёт
файлы с адреса, до которого доезжают российские операторы.

### Вариант А — Beget VPS (выбран)

Сервер уже оплачен под соседний проект «Деловой Портрет» (`d-portret.ru`,
IP `159.194.210.112`), и его мощности с запасом хватает: наш сайт — 3 МБ
статики и ~150 визитов в день. Марджинальная стоимость нулевая.

**Как выкладываем.** Не по SSH: среда разработки ходит наружу только по
HTTPS, SSH оттуда недоступен. Поэтому инициатива у сервера — он сам
забирает готовую сборку из отдельной ветки git. Ровно та же схема, к
которой пришёл соседний проект (`headshot-bot/deploy/self_deploy.sh`).

Цепочка получается такая:

```
здесь:   npm run build → ./scripts/publish-dist.sh → ветка deploy/nalog-servis-dist
сервер:  systemd-таймер раз в 5 минут → git fetch → rsync в /var/www/nalog-servis
```

В ветке `deploy/nalog-servis-dist` лежит только содержимое `dist/` — ни
исходников, ни истории; сервер клонирует её с `--depth 1`.

**Разовая настройка на сервере** (выполнить один раз под root):

```bash
# 1. Код выкладки и веб-корень
mkdir -p /opt/nalog-servis /var/www/nalog-servis
cd /root/src && git fetch origin claude/tax-deduction-declaration-site-dfit30 \
  && git checkout origin/claude/tax-deduction-declaration-site-dfit30 -- deploy
cp /root/src/deploy/nalog-servis-pull.sh /opt/nalog-servis/
chmod +x /opt/nalog-servis/nalog-servis-pull.sh

# 2. nginx (свой server_name, default_server соседа не трогаем)
cp /root/src/deploy/nginx-nalog-servis.conf /etc/nginx/sites-available/nalog-servis
ln -sf /etc/nginx/sites-available/nalog-servis /etc/nginx/sites-enabled/
nginx -t && systemctl reload nginx

# 3. Первая выкладка и таймер
/opt/nalog-servis/nalog-servis-pull.sh
cp /root/src/deploy/nalog-servis-pull.{service,timer} /etc/systemd/system/
systemctl daemon-reload && systemctl enable --now nalog-servis-pull.timer

# 4. TLS (домен кириллический — certbot работает с punycode)
certbot --nginx -d xn----7sbhcltqolxje.xn--p1ai -d www.xn----7sbhcltqolxje.xn--p1ai
```

**Только после этого** — переключить A-записи домена у регистратора на
`159.194.210.112`. Порядок важен: если переключить раньше, посетители
попадут на `default_server` соседнего проекта.

Проверить, что таймер живёт: `systemctl list-timers | grep nalog-servis`,
журнал выкладок — `/var/log/nalog-servis-deploy.log`.

**Риски варианта:**

* **Общая точка отказа с «Деловым Портретом».** Упал сервер — упали оба
  сайта. Пока идёт переходный период, GitHub Pages остаётся собранным:
  A-записи возвращаются назад за время TTL.
* **Общие ресурсы.** Статика почти ничего не ест, но диск и трафик общие.
* **Сертификат.** `certbot renew` ставится таймером при установке; стоит
  один раз проверить `systemctl list-timers | grep certbot`.

### Вариант Б — Яндекс Облако Object Storage (запасной)

Имеет смысл, если VPS окажется занят или захочется убрать администрирование:
управляемый сервис, ни ОС, ни nginx, ни продления сертификатов. Стоит около
100 ₽/мес при нынешнем трафике. Скрипт выкладки под него готов —
`scripts/deploy-static.py`, работает с любым S3 (Яндекс, Timeweb, VK Cloud).

Шаги: бакет с публичным чтением → в настройках «Веб-сайт» указать
`index.html` и главной, и страницей ошибки (для SPA обязательно) →
сервисный аккаунт с ролью `storage.editor` и статическим ключом → домен и
бесплатный TLS → A-записи.

Ключи дописываются в `/root/.ndfl-tokens`:

```
S3_ENDPOINT=https://storage.yandexcloud.net
S3_BUCKET=nalog-servis
S3_KEY_ID=...
S3_SECRET=...
```

### Чего делать НЕ надо

* Ставить перед GitHub Pages зарубежный CDN (Cloudflare) — он попадает под
  ту же фильтрацию, получится тот же сюрприз второй раз.
* Менять hash-роутер на обычный до переезда: сейчас это лишний риск, а
  выигрыш в SEO появится только когда сайт станет стабильно доступен.

## Про выкладку

Оба скрипта заливают только изменившееся, ставят `no-cache` на
`index.html` и вечный кэш на файлы из `assets/` (у них хеш в имени) и
убирают устаревшие файлы. Порядок в VPS-варианте важен: сначала assets,
потом index.html — иначе на секунду возможен index, ссылающийся на ещё
не залитые чанки.

## Проверка после переезда

1. `dig налог-сервис.рф` — адреса больше не 185.199.108–111.153.
2. Открыть сайт у того провайдера, где сейчас таймаут.
3. Через сутки сверить в Метрике клики и визиты: `ym:ad:clicks` против
   `ym:ad:visits` должны сойтись (норма — расхождение до 10 %).

Ветка `claude/react-website-wi5fnz` и GitHub Pages какое-то время
остаются как запасная площадка — выключать их стоит только после того,
как новый хостинг отработает без сбоев неделю.
